# 1. Исходная точка

GFORT — финансовый Telegram Mini App с пользовательским кабинетом,
депозитами и выплатами в USDT BEP-20, партнёрской системой,
уведомлениями и административной панелью. Базовая архитектура обновлений
— V10.5 Safe Deploy; кандидат V10.6 предусматривает изменение
реферального баланса, ручное открытие инвестиций и управление доступом к
уровням партнёрской программы.

- **Production не является средой разработки.** Все изменения
  выполняются в отдельном кандидате релиза.

- **Существующие данные сохраняются.** Пользователи, балансы,
  инвестиции, выплаты, история, конфигурация и secrets не пересоздаются
  ради редизайна.

- **Один источник изменений.** Только текущая рабочая сессия Cursor
  редактирует код; параллельные агенты и несведённые ветки не
  используются.

- **Telegram-first.** Интерфейс проверяется в мобильном WebView на
  Android/iOS, с safe-area, системной кнопкой Back, клавиатурой и
  нестабильной сетью.

- **Русская локализация полная.** Если выбран русский язык, toast,
  modal, validation, empty/error/offline states и сообщения API не
  показываются на английском.

# 3. Постоянные правила Cursor

Перед первой кодовой итерацией Cursor создаёт проектное правило
\`.cursor/rules/gfort-safety.mdc\` со следующими требованиями:

- Не выводить и не копировать seed phrase, bot token, private RPC/WSS,
  \`.env\` и содержимое \`secrets\` в чат, diff, тестовый fixture,
  screenshot или лог.

- Не изменять финансовые формулы и существующие записи без отдельной
  задачи владельца.

- Перед правкой прочитать затрагиваемые файлы, проследить data flow и
  перечислить предполагаемые изменения.

- Не выполнять deploy, destructive SQL, удаление
  state/data/backups/releases или \`--fresh\` без прямого разрешения.

- Каждая финансовая mutation должна быть серверно авторизована,
  валидирована, атомарна, идемпотентна и зафиксирована в audit trail.

- После каждой итерации показать изменённые файлы, краткий diff summary,
  выполненные тесты, риски и незакрытые вопросы.

- При конфликте дизайна и безопасности приоритет имеют сохранность
  средств, корректность данных и обратимость релиза.

# 9. Технические стандарты

- **Компонентность:** design tokens и reusable components вместо
  точечных дублирующихся CSS-правок.

- **API:** явные request/response schemas, единый error envelope,
  серверная авторизация каждого admin endpoint и обратная совместимость.

- **Финансовые данные:** целые minor units, SQLite transaction,
  idempotency key и audit trail.

- **Blockchain:** один nonce controller, reconciliation с chain,
  отсутствие новой подписи при неоднозначном broadcast и сохранение raw
  tx.

- **Секреты:** не возвращаются во frontend и не появляются в HTML,
  browser storage, installer output или application logs.

- **Accessibility:** touch target ≥ 44 px, contrast, keyboard/focus,
  aria labels и отсутствие передачи смысла только цветом.

- **Performance:** ленивая загрузка тяжёлых разделов, компактный
  bootstrap, отмена stale requests и отсутствие утечек timers/listeners.

- **Observability:** структурированные события без секретов, понятные
  error codes, worker freshness и audit correlation ID.

# 12. Definition of Done

- Все согласованные пользовательские и административные экраны
  реализованы и проверены на целевых размерах.

- В русском режиме нет английских системных сообщений, наложений текста,
  обрезанных модальных окон и недоступных кнопок.

- Новые admin controls атомарны, идемпотентны и содержат actor, reason,
  timestamp, before/after и correlation ID.

- Финансовый regression suite подтверждает неизменность существующих
  расчётов и очередей.

- Новая чистая сессия Cursor закрыла все P0/P1; P2 либо исправлены, либо
  письменно приняты владельцем.

- Installer проходит shell/build/self-tests, payload hash verification,
  backup check и rollback rehearsal.

- Подготовлены release notes, список изменённых файлов, команда
  установки и post-deploy checklist.
